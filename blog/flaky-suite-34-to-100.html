How I took a flaky regression suite from 34% to 100%

October 2026 · ~6 min read

When I joined Statflo as a QA Analyst, the Playwright/TypeScript end-to-end suite passed 34% of the time. At that rate, a red run tells you nothing. Nobody can tell a real regression from noise, so people stop looking, and the suite becomes something the team runs out of habit rather than something it trusts.

Today the same suite passes 100% on a healthy build, with no tests I'd call flaky. There was no single big fix. It came from a handful of habits, and these are the ones that mattered most.

1. "Flaky" is a diagnosis, not an explanation

The easiest thing to do with an intermittent failure is to add a retry and move on. I made a rule for myself instead: every failure gets classified as one of three things before anything changes:

  • Test bug: the test is wrong, racy, or depends on something it doesn't control.
  • Environment issue: DNS, a third-party sandbox, a deploy happening mid-run.
  • Application bug: the product really is broken, sometimes only under timing the test happens to hit.

That third category is the reason not to paper over failures. A surprising number of "flaky tests" turned out to be real product issues that only showed up under load or bad timing. Those are exactly the bugs a regression suite exists to catch.

2. Most of the flakiness was race conditions in the tests

The single most common pattern was an action followed by a wait for the network response it triggers:

// Racy: the response can arrive before we start listening
await page.getByRole('button', { name: 'Save' }).click();
await page.waitForResponse(r => r.url().includes('/api/contacts'));

On a fast run, the response lands between those two lines and the wait hangs until it times out. The fix is to start listening before acting:

// Safe: the listener exists before the request is sent
const saved = page.waitForResponse(r => r.url().includes('/api/contacts'));
await page.getByRole('button', { name: 'Save' }).click();
await saved;

The same idea applies to typing into search fields, dialogs that load data on open, and anything else where the UI kicks off a request. Once I started looking for "act, then wait", I found it all over the suite.

3. Parallel workers expose shared test data

Running tests in parallel is the obvious way to make a suite faster, and it's also the fastest way to find out which tests share data. Two tests editing the same contact, or sharing one logged-in session, will pass alone and fail together.

What helped:

  • Each test creates the data it needs, ideally through the API rather than the UI, and cleans up after itself.
  • Each worker gets its own authenticated session instead of sharing one.
  • Fixtures that genuinely have to be shared get guarded: set up a known state before the test and restore it afterwards.

With those in place I made the CI worker count configurable from 1 to 6. Running at 1 worker is a useful experiment in itself: if a test still fails with no parallelism, concurrency isn't the cause.

4. Reporting that people actually read

A suite that's green isn't much use if nobody sees the result. Three things made results visible:

  • Allure with history, published to GitHub Pages per environment, so trends are visible and a test that fails once in twenty runs stands out.
  • Slack summaries after each run, listing failures and the reason for each, so the team knows within minutes whether a release is healthy.
  • Spec-level test contracts: a short description of what each spec covers, checked in CI so the documentation can't drift away from the code.

5. Make CI cheap to run

One smaller but satisfying fix: the repository had grown to 26 GB. Bringing it down to 80 MB (a 99.7% cut) meant every pipeline stopped spending time on clone and checkout before running a single test. When CI is quick and cheap, people run it more often, and frequent runs are how you find intermittent issues.

What I'd tell someone starting the same job

Don't trust a green run until you'd trust a red one. Before tuning anything for speed, make every failure mean something. Then speed it up.
